# 01 / 系统拓扑架构与 STRM 极速直链原理解析

## 一、 为什么抛弃传统的 WebDAV 挂载与全量下载？

家庭影音玩家在搭建 NAS 影视库时，通常经历过三个历史阶段：

1. **传统本地仓储时代（机械硬盘狂魔）**：
   - 购买 4 盘位、8 盘位甚至 16 盘位的 NAS，疯狂塞入 16TB 机械硬盘；
   - 痛点：设备昂贵、电费惊人、硬盘噪音共振剧烈，而且每部 4K REMUX 动辄 50GB~80GB，下载耗时长，看完舍不得删，空间永无止境地告急。
2. **传统 WebDAV 云端挂载时代（痛不欲生）**：
   - 借助 WebDAV 挂载网盘为本地盘符，直接让 Emby / Jellyfin / 飞牛影视扫描；
   - 痛点：媒体库定时全盘扫描或海报刮削时，NAS 会向网盘发起几十万次 API 遍历请求，直接触发网盘服务端的**高频封号或限速限流（429 Too Many Requests）**；同时播放时通过 NAS 内存推流中转，内网带宽与 CPU 吃满，拖动进度条频繁转圈卡顿。
3. **STRM 虚拟文本直链时代（无人驾驶终极形态）**：
   - 物理文件保留在 115 / 夸克网盘官方 CDN；
   - 本地仅存储几 KB 的 `.strm` 纯文本文件，里面仅包含该视频对应的网盘官方直链；
   - 播放器直接向网盘 CDN 请求视频分块切片，NAS 仅做元数据呈现与直链解析，**彻底实现“零硬盘占用、首播 913ms、拖拽 518ms、零封号风险”**。

## 二、 核心原理：什么是 STRM？

STRM 是绝大多数主流现代播放器（飞牛影视、Kodi、Emby、Jellyfin、Infuse）原生支持的流媒体文本标准。

一个标准的 STRM 文件极其简单：
- 文件扩展名：`.strm`
- 文件体积：通常仅 **1 KB ~ 4 KB**
- 文件内容：只有单行纯文本，指向 SmartStrm 本地代理或上游网盘的 HTTP 直链：
  ```text
  http://127.0.0.1:8024/smartstrm_fid/115_main/6829104819028471
  ```

### 播放时的 302 重定向与 HTTP 206 分块传输
1. 客户端（电视端飞牛 App / 手机 / Apple TV）点击播放；
2. 飞牛影视在本地毫秒级读取几 KB 的 `.strm` 文件；
3. SmartStrm 守护进程将该请求重定向至 115 或夸克网盘官方 CDN；
4. 播放器直接与网盘 CDN 握手，发起 `Range: bytes=0-1024` 分块请求；
5. CDN 返回 `HTTP/2 206 Partial Content`，无需全量下载即可毫秒级起播与任意跳转！

## 四、 核心铁律：为什么必须“改名先行”？

在所有自动化影视流水线中，**时序是决定成败的根本生命线**：

```text
[搜源转存] ➔ [网盘标准化改名] ➔ [生成 STRM 直链] ➔ [镜像同步] ➔ [飞牛入库]
   ❌ 严禁顺序颠倒！
```

### 为什么不能先生成 STRM 再改名？
- STRM 文件内部记录的是**生成那一刻网盘文件的固定路径与文件 ID**；
- 如果你先生成了 STRM，再去网盘重命名或移动分类，原本生成的 `.strm` 文件将**全量瞬间变成死链**；
- 飞牛影视播放死链会直接抛出 `HTTP 500 视频文件找不到`，导致媒体库彻底崩溃。
- 因此：**必须先完成标准化命名，再触发 SmartStrm 生成直链！**
